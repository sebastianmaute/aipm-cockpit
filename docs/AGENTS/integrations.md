#### Closed months (§699)

- **The close is per project set.** The TimeLog panel's only fetch is by project (`fetchBookingsForProjects`), and it records nobody in `dailyUsers` (deliberately, §366). A complete project fetch does prove every booking on its projects, whoever made it, so the close is scoped to the TimeLog project ids the closed months were fetched over, and a person's hours on other projects are out of scope.
- **Every booker, not only linked people (spec section 10).** Stored `userLinks` hold only manual pins; the panel's automatic matches (`autoMatchUsers`) are never written back, so a links-based close protected nobody on a team matched by email. Links are therefore not an input to the close, the rule or the certifier. They only NAME a violation's person, the same way the other five rules do: the stored link's `resourceId`, or `null`, which the insight shows as `#<TimeLog id>`.
- **What `close` stores.** `TimelogLinks.close` (`TimelogMonthClose` in `timelog-types.ts`) is `{ through, projectIds, saved }`. `through` is the last closed month (`YYYY-MM`; every earlier month is closed too). `projectIds` is the project set, recorded by the first close and kept by every later one: unique positive integers, ascending, non-empty. `saved` maps month, then TimeLog user id, then day to the hours the roll held: every positive user id with a booking in that month, negative day totals (TimeLog corrections) included. A cell the roll cannot read (`isDailyCell`) and a non-positive id are skipped. A person with NO key in a month is compared against `{}`, so a new booker in a closed month is flagged for every booking there.
- **Who a booking belongs to.** v2 rows carry initials only. `fetchBookingsForProjects` resolves them with `initialsToUserId` (`timelog-match.ts`) over the WHOLE TimeLog directory, inactive users included, so a person deactivated after a close is not read as having deleted every booking (an unresolved row becomes `userId: 0`, which `buildDailyRoll` drops). On an initials clash a displayable (active) user wins, so a row that resolved before still resolves to the same person. The People table (`users`, `displayableUsers`) still hides inactive users, so they are never auto-matched; their hours reach a resource only through a manual pin.
- **The cache's project scope.** `ActualsCacheEntry.dailyProjects` (`timelog-actuals-store.ts`) holds the ids a project fetch covered (`fetchBookingsForProjects` stores its unique ids, ascending). A person fetch (`fetchBookings`) leaves it absent, and absent means "project scope unknown". It follows `dailyUsers` everywhere in the store: checked on read (a non-list or a non-positive-integer member drops the field), shed together with `daily`, `dailyWindow` and `dailyUsers` when the roll trim keeps no cell and by size-budget stages 2 and 6, and carried on every save through `rollPair` in `use-timelog-sync.ts`, because a saver that omits a field clears it (§172).
- **Persistence.** `close` rides the `TimelogLinks` meta-blob whole through all six write paths. Only `sanitizeTimelogLinks` changed (via `sanitizeTimelogClose`): a hand-edited or corrupt `close`, `projectIds` included, drops WHOLE with a `timelog.close-dropped` diagnostic and never partly survives. An hours value may be any finite number, negative included; `NaN`, `Infinity`, a string or `null` drops the whole close. It is ABSENT, never `{}`, when nothing is closed, and `isBlankTimelogLinks` requires `close === undefined` so a blob holding only a close is not discarded.
- **Closing, reopening and accepting** are pure functions in `timelog-month-close.ts` (`closeNextMonth`, `reopenLastMonth`, `acceptMonth`); the UI is `timelog-month-close-panel.tsx`. `closeNextMonth` refuses with a `MonthCloseRefusal`, the first failing check winning, in this order: `no-roll`, `not-ended` (the month has not ended; `today` is the UTC date, matching the fetch window), `window-start`, `window-end`, `partial`, `no-projects` (the cache has no `dailyProjects`, or an empty one) and `projects-changed` (a close exists and the cache's `dailyProjects` is a different set from `close.projectIds`; order and duplicates do not matter, `sameProjectSet`). Reopening steps back one month and keeps `projectIds`, and reopening the last one deletes `close`. Changing the project set means reopening every closed month, which discards their saved hours; reopening only the last month keeps `projectIds`, so the next close is refused with `projects-changed`. `acceptMonth` accepts a reviewed change: it refuses `not-closed` unless the month has a `saved` key and is `<= through`, then applies the close's refusals for that month, and on success replaces `saved[month]` with the current bookers' cells, keeping `through` and `projectIds`. The panel offers it for a chosen closed month behind an in-page confirmation; only one confirmation row (reopen or accept) is open at a time, and a refusal the close already states is not repeated.
- **The panel** also lists the close's TimeLog projects by name from the cached `projectRefs` (`timelogProjectLabel`), falling back to the id, and its first-month select offers at least the last 12 ended months, reaching back to the month the cached `dailyWindow` starts in when that is older.
- **The rule** is `evaluateClosedMonth` (`timelog-closed-month.ts`), called from `evaluateTimelogPolicy`. Only months with a `saved` entry are checked, and a month counts as covered only when the fetched window spans it from its first day to its last and the cache's `dailyProjects` equals `close.projectIds`. When the sets differ no month is covered: the rule emits nothing and stays out of `evaluated`, so stored flags freeze until the same projects are fetched again or the months are reopened. In every covered month it checks every user id in `saved[month]` or holding a readable roll cell in that month; `dailyUsers` plays no part in this rule (the other five rules still use it). A missing day counts as 0 on either side, and a day is changed when `Math.abs(change) >= CLOSED_MONTH_TOLERANCE_HOURS - 1e-9` (8 to 8.01 is flagged; 8 to 8.004 and a 0.006 h change are not). The engine input has a REQUIRED `partial` and a REQUIRED `dailyProjects` key (it may be undefined): while a fetch is partial the rule emits nothing and stays out of `evaluated`; a person-month holding an unreadable cell raises nothing and also keeps the rule out of `evaluated`. ★ That last case is reachable only by a caller handing over an unvalidated roll: `loadActualsCache` strips a cell failing `isDailyCell` on read, so a corrupted stored cell reads as ZERO (a saved day reads as deleted and is flagged), not as unreadable. With nothing closed it is evaluated and clean even on a partial roll.
- **`closedMonthCertifies`** (`timelog-closed-month.ts`, re-exported from `timelog-policy.ts` together with `CLOSED_MONTH_TOLERANCE_HOURS`) is why a partly covered month cannot clear a flag. The runner (`use-insight-lifecycle.ts`) asks it whether a stored insight over the flag's first to last violation date may be cleared, passing the cache's `dailyProjects`. It returns true when `close` is null. It returns false for a malformed or inverted span. Otherwise it walks only the months from the first to the last violation date. A month after `through` (reopened) passes, so reopening the last month clears its flags rather than freezing them. Every other month needs ALL of: a non-partial fetch, `dailyProjects` the same set as `close.projectIds`, and the month in `closedMonthsCovered`; otherwise it returns false and the flag freezes. Links play no part, so an unlinked person's flag clears like anyone's; after `acceptMonth` the month's flag clears on the next evaluation.
